# Targeted Review — `lib/ntrip-client` (2026-02-10)

## Scope and objective

This review covers the library code and bundled examples under `lib/ntrip-client`, with focus on:

- coding consistency
- dead code from past evolution
- abstraction opportunities
- logging improvements
- efficiency optimization
- build flags rationalization
- comments quality

Guiding criterion: **`ntrip-client` should be an autonomous library** (usable as a standalone component without hidden dependencies on the parent application architecture).

---

## Executive summary

The library already has a solid baseline (clear API, optional logger callback, RTCM parser isolation, Rev2→Rev1 fallback). The main technical debt is around **task lifecycle robustness**, **thread-safety semantics**, **autonomy boundary (examples + platform coupling)**, and **high-frequency overhead in the streaming loop**.

The highest-impact proposals are:

1. Add explicit task lifecycle control (`start/stop/join` semantics) and prevent duplicate task spawn.
2. Make state and stats synchronization policy explicit and consistent.
3. Remove/replace hidden application-level dependencies in examples (`extern bool isInternetReachable`).
4. Introduce compile-time feature flags to decouple Arduino/FreeRTOS assumptions.
5. Reduce loop overhead (mutex frequency, `millis()` churn, avoid repeated semaphore creation checks).

---

## Detailed proposals (what / why / how)

## 1) Coding inconsistency: mixed synchronization model

### What
`_stats` is protected with `statsMutex`, while `_state`, `_healthy`, `failures`, `lastAttempt`, and `lastHealth` are accessed from multiple contexts with no consistent synchronization policy.

### Why
This can produce hard-to-reproduce races (especially on dual-core ESP32), stale reads in UI/monitor code, and behavior that depends on timing.

### How
- Define and document a strict policy, for example:
  - **Option A**: all mutable runtime state behind a single state mutex.
  - **Option B**: atomics for scalar state (`_state`, `_healthy`, counters), mutex only for `String` and aggregate structs.
- Keep `NtripStats` as a snapshot object, but isolate write path in one helper (`updateStats(...)`).
- Add a short `Thread-safety contract` section in `README.md` and header comments.

---

## 2) Dead code: unreachable `delete[] buffer`

### What
`taskLoop()` has `for (;;)` infinite loop and `delete[] buffer;` after it, which is unreachable.

### Why
This is classic dead code and indicates missing cooperative shutdown path for the worker task.

### How
- Add a `volatile/atomic bool running` flag.
- Turn `for (;;)` into `while (running)`.
- Implement a real stop sequence that exits loop, frees buffer, and deletes task cleanly.
- Optionally move buffer to RAII (`std::unique_ptr<uint8_t[]>` when toolchain allows) or a static scratch buffer policy.

---

## 3) Dead code / lifecycle drift: `startTask()` can be called repeatedly

### What
`startTask()` always calls `xTaskCreatePinnedToCore(...)` and does not store task handle or guard duplicate creation.

### Why
Multiple background tasks can process same client instance concurrently, causing socket conflicts, double reconnect loops, and inconsistent stats.

### How
- Add `TaskHandle_t taskHandle` member.
- If task already running, return false or log warning and no-op.
- Add `isTaskRunning()` accessor for diagnostics.

---

## 4) Abstraction gap: transport and scheduler are hard-coupled

### What
Current implementation tightly binds to `WiFiClient`, FreeRTOS APIs (`xTaskCreatePinnedToCore`, semaphores), and Arduino timing (`millis`, `vTaskDelay`).

### Why
This limits reusability across environments and conflicts with the “autonomous library” criterion.

### How
Introduce narrow interfaces:
- `INtripSocket` (connect/read/write/available/connected/stop)
- `INtripClock` (`nowMs`, `sleepMs`)
- optional `INtripTaskRunner` for threaded mode

Then provide default adapters for Arduino/ESP32. This preserves current behavior while enabling host-side tests and non-FreeRTOS integration.

---

## 5) Abstraction opportunity: split protocol session from task orchestration

### What
`taskLoop()` currently mixes:
- connection state machine
- protocol negotiation (HTTP/NTRIP)
- stream validation/parsing
- health policy
- metrics updates

### Why
Single large loop is harder to unit test and harder to evolve without regressions.

### How
Refactor into composable units:
- `NtripSession` (HTTP request/response + stream bytes)
- `RtcmHealthMonitor` (strict validation + passive sampling + zombie detection)
- `NtripSupervisor` (retries/lockout/backoff)

Keep `NtripClient` as façade.

---

## 6) Logging enhancement: low cardinality machine-readable event IDs

### What
Logs are currently free-form strings. They are human-friendly but not ideal for aggregation/alerting.

### Why
In production telemetry, stable event IDs simplify searching and dashboards.

### How
- Add event enum/code with each log callback (or include in message prefix), e.g. `NTRIP_EVT_CONNECT_FAIL`, `NTRIP_EVT_ZOMBIE_TIMEOUT`.
- Keep text message for readability.
- Include relevant structured fields (attempt, host, timeout, bytes/s) in log format.

---

## 7) Logging enhancement: add rate-limited warnings

### What
Warnings like “No preamble in sample” can recur indefinitely at fixed interval.

### Why
Can flood logs and obscure critical transitions.

### How
- Add per-event rate limiter (e.g., emit at most every N seconds unless state changes).
- Optionally expose counters via stats for suppressed logs.

---

## 8) Logging enhancement: explicit connection context at failure

### What
Some error paths only record a textual message without full context.

### Why
Field debugging is faster when every failure includes target endpoint, protocol revision, attempt counters, and elapsed timings.

### How
Extend `setError(...)` call sites to include context-rich formatted text and/or dedicated error metadata struct stored in stats.

---

## 9) Efficiency optimization: high-frequency mutex traffic in hot loop

### What
Within streaming loop, stats mutex is taken frequently (bytes, frames, crc, uptime), including every ~10ms.

### Why
On constrained targets, semaphore churn can cost CPU and increase contention.

### How
- Keep local counters in task context; flush to shared stats on lower cadence (e.g., every 250ms).
- Update `totalUptime` lazily when `getStats()` is called, or once per second.
- Batch updates inside single mutex acquisition per cycle.

---

## 10) Efficiency optimization: repeated `ensureMutexes()` in fast paths

### What
`ensureMutexes()` is repeatedly called in operational code paths.

### Why
Even when successful, repeated checks add overhead and muddy control flow.

### How
- Create mutexes once in `begin()`; fail hard if not available.
- Remove repetitive checks from hot path; assume invariant “begin succeeded → mutexes valid”.
- Keep defensive asserts in debug builds.

---

## 11) Efficiency/correctness: connection header semantic mismatch

### What
Rev2 request sets `Connection: close` while expecting long-lived stream.

### Why
Some servers may still keep stream open, but header is semantically contradictory and may reduce compatibility.

### How
Use `Connection: keep-alive` (or omit header) for streaming mode; document expected caster behavior.

---

## 12) Build flags rationalization: define explicit feature toggles for autonomy

### What
Library has no visible compile-time feature matrix (threaded mode, parser strictness, passive scan depth, logging verbosity).

### Why
Consumers cannot tailor footprint/behavior without editing source.

### How
Add optional compile-time flags with sane defaults:
- `NTRIP_CLIENT_ENABLE_TASK=1`
- `NTRIP_CLIENT_ENABLE_REV1_FALLBACK=1`
- `NTRIP_CLIENT_PASSIVE_SCAN_BYTES=128`
- `NTRIP_CLIENT_LOG_LEVEL_DEFAULT=...`
- `NTRIP_CLIENT_THREAD_SAFE_STATS=1`

Document each in `README.md` and keep backward compatibility.

---

## 13) Build flags rationalization: platform capability gates

### What
Code assumes FreeRTOS+ESP32 APIs are present whenever compiled.

### Why
Porting friction increases and compile errors become opaque outside ESP32 context.

### How
- Guard platform-specific code via feature macros and static assertions with actionable messages.
- Provide non-task mode (`poll()` API) for platforms without `xTaskCreatePinnedToCore`.

---

## 14) Comments/documentation improvement: remove stale or contradictory wording

### What
Some comments over-explain obvious lines while key behavior contracts are undocumented (e.g., thread ownership, who may call `begin/startTask/stop`, guarantee around reconnect timing).

### Why
Low-value comments add noise; missing behavioral comments create integration mistakes.

### How
- Replace line-by-line comments with section-level intent comments.
- Add API contract comments in header:
  - required call order
  - thread-safety of each method
  - blocking behavior
  - ownership/lifetime assumptions for `Print&`.

---

## 15) Autonomy criterion gap in examples

### What
`examples/basic` and `examples/production` depend on `extern bool isInternetReachable`, which implies external project symbols.

### Why
Examples should compile standalone; current form conflicts with “autonomous library” and can confuse adopters.

### How
- Make internet status local to example (derive from `WiFi.status()` internally).
- Or provide a tiny connectivity abstraction in the example itself.
- Ensure each example is fully self-contained and buildable in isolation.

---

## 16) Dead/duplicated example code from past development

### What
`examples/basic/main.cpp` and `examples/production/main.cpp` are highly overlapping.

### Why
Duplication causes maintenance drift and inconsistent fixes over time.

### How
- Keep one canonical “production” example and one truly minimal one.
- Move shared utilities (JSON config helpers, stats printers) into a shared example support header/source.
- Mark advanced differences explicitly.

---

## 17) API robustness improvement: validate config at `begin()`

### What
No strict early validation for empty host/mount/credentials, invalid buffer sizes, zero timeouts, etc.

### Why
Misconfiguration currently fails late during connect; diagnostics are weaker and loops may spin unexpectedly.

### How
- Add `validateConfig(const NtripConfig&)` with explicit errors.
- Reject invalid ranges at startup and return false with actionable `lastErrorMessage`.

---

## 18) Health-check policy abstraction

### What
Passive health check scans first N bytes for preamble (currently fixed behavior in-loop).

### Why
Different streams and packetization patterns may require different heuristics; current one can miss healthy streams and trigger false zombie detection.

### How
- Make sampling strategy pluggable or parameterized (scan window, cadence, fallback to periodic full-parse chunk).
- Expose policy knobs in config or compile-time defaults.

## Proposed test plan (to implement)

## A. Unit tests (host-side, no hardware)

1. **RTCM parser happy path**
   - Feed known valid frame byte-by-byte.
   - Assert `valid=true`, correct message type, length.

2. **RTCM parser CRC failure path**
   - Flip one payload bit.
   - Assert `crcError=true`, no valid flag.

3. **Parser resynchronization**
   - Feed random noise, partial frames, then valid frame.
   - Assert parser recovers and outputs valid result.

4. **Config validation**
   - Invalid host/mount/timeouts/buffer combinations.
   - Assert deterministic validation errors.

5. **HTTP response parser behavior**
   - Simulate ICY 200, HTTP 200, 401, 404, timeout.
   - Assert mapped `NtripError` and messages.

## B. Component tests (mock socket/clock)

6. **Rev2 fallback to Rev1**
   - Mock Rev2 failure + Rev1 success.
   - Assert only expected retries and resulting streaming state.

7. **Lockout behavior**
   - Force consecutive failures > `maxTries`.
   - Assert transition to `LOCKED_OUT` and no reconnect until reset.

8. **Zombie stream detection**
   - Simulate data starvation after initial valid frames.
   - Assert timeout detection and reconnect flow.

9. **Passive sampling false-negative guard**
   - Feed chunks where preamble appears beyond scan window.
   - Validate policy behavior (and test improved strategy once implemented).

10. **Statistics consistency under load**
    - High-rate mocked stream with concurrent stats reads.
    - Assert monotonic counters and no torn snapshots.

## C. Concurrency/lifecycle tests

11. **Duplicate start protection**
    - Call `startTask()` twice.
    - Assert second call is rejected/no-op and only one task runs.

12. **Graceful stop**
    - Start, stream, stop.
    - Assert task exits cleanly and resources freed.

13. **Reset/reconnect semantics**
    - Enter lockout, call `reset()` and `reconnect()`.
    - Assert immediate attempt and expected state transitions.

## D. Example build tests

14. **Standalone example compile checks**
    - Each example compiles independently (no external symbols).

15. **Feature-flag matrix smoke tests**
    - Build with task mode on/off, Rev1 fallback on/off, reduced scan bytes.
    - Ensure successful compile and basic startup behavior.

---

## Suggested implementation order

1. Lifecycle + synchronization invariants (`start/stop/task handle`, mutex policy).
2. Config validation + richer errors.
3. Performance pass (batch stats updates, reduce mutex churn).
4. Abstraction layers (socket/clock/task runner) to improve autonomy and testability.
5. Example cleanup and de-duplication.
6. Build-flag matrix + documentation refresh.
7. Test suite rollout (unit → component → lifecycle → build matrix).

---

## Expected outcomes

If the above proposals are implemented, `ntrip-client` should gain:

- safer multi-core behavior
- cleaner lifecycle management
- lower runtime overhead
- stronger observability and debuggability
- simpler portability and host-side testing
- examples that truly represent a standalone autonomous library
