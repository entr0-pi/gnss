# Codebase Review — 2026-02-10

## Scope and method

This review covers firmware (`src/`, `include/`), build/configuration (`platformio.ini`, `utils/build-tester/`), and project documentation (`README.md`, `include/README.md`).

Review goals addressed:
- coding consistency
- dead code / legacy leftovers
- abstraction opportunities
- logging enhancements
- efficiency optimization
- build flags rationalization
- comments improvement
- proposed tests to implement

---

## Executive summary

The project is generally well organized and readable, but there are recurring patterns that should be consolidated and some correctness/documentation mismatches around build flags and config sources.

Most impactful improvements:
1. **Fix preprocessor-flag consistency and UI lock semantics** (`#ifdef` vs `#if`) for `FORCE_HARDCODED_UART`.
2. **Centralize WiFi config loading/validation** to remove duplicated parsing logic.
3. **Reduce heap fragmentation risk** in HTTP/JSON response building.
4. **Harden observability** with structured counters and periodic health logs.
5. **Rationalize flag matrix and docs** to align defaults, dependencies, and tested combinations.

## Detailed proposals

## 1) Coding inconsistency

### 1.1 Inconsistent compile-time flag checks (`#ifdef` vs numeric flags)
**What**
- In `web_ui.cpp`, UART lock checks use `#ifdef FORCE_HARDCODED_UART`.
- Elsewhere, flags are treated numerically (`#if FORCE_WIFI_SECRETS`, `#if WEBUI_ENABLE`, etc.).

**Why**
- `#ifdef` checks *definition*, not *value*; `-DFORCE_HARDCODED_UART=0` still behaves as “enabled”.
- This produces surprising behavior and diverges from other flags’ semantics.

**How**
- In `include/app.h`, add a default:
  - `#ifndef FORCE_HARDCODED_UART`
  - `#define FORCE_HARDCODED_UART 0`
- Replace `#ifdef FORCE_HARDCODED_UART` in `web_ui.cpp` with `#if FORCE_HARDCODED_UART`.
- Keep a single “numeric boolean flag” convention for all optional features.

**Priority**: High

---

### 1.2 Header fallback type issue in `ntrip_client.h`
**What**
- In disabled mode (`#else`), inline fallback uses `NtripClientSnapshot` type without declaring it.

**Why**
- This is fragile and can break compile units that include the header while `NTRIP_CLIENT_ENABLE=0`.

**How**
- Either:
  1. Define `struct NtripClientSnapshot` unconditionally; or
  2. Remove/replace fallback signature so it doesn’t reference undefined type.

**Priority**: High

---

### 1.3 Naming and style consistency (mixed local helper styles)
**What**
- Different naming styles coexist for equivalent helper purposes (e.g., `parseIpField` lambda in `main.cpp` vs `parse_ip_field` function in `wifi_config.cpp`).

**Why**
- Small style drift increases cognitive load and tends to grow over time.

**How**
- Adopt and document one naming convention for internal helpers (`snake_case` or `camelCase`).
- During refactor (proposal 3.1), unify helper names and move shared routines to `wifi_config.*`.

**Priority**: Medium

## 3) Opportunities to increase abstraction

### 3.1 Centralize WiFi config loading, fallback, and validation pipeline
**What**
- WiFi config flow spans multiple places:
  - NVS load/save in `wifi_config.cpp`
  - JSON file parsing fallback in `main.cpp`
  - field validation repeated in route handlers

**Why**
- Repetition increases bug surface and makes behavior divergence likely.

**How**
- Add a small service layer in `wifi_config.*`:
  - `wifi_config_load_effective(...)` (NVS -> file -> compile-time fallback)
  - `wifi_config_validate(...)`
  - `wifi_config_source` enum for telemetry/logging
- Keep `main.cpp` as orchestration only.

**Priority**: High

---

### 3.2 Abstract repetitive Web API JSON response pattern
**What**
- Many handlers repeat the same pattern:
  - parse request
  - build `JsonDocument`
  - `serializeJson` to `String`
  - send headers + response

**Why**
- Boilerplate repetition makes behavior inconsistent over time and increases maintenance effort.

**How**
- Add helper wrappers in `web_ui.cpp` (or a tiny `http_utils.*`):
  - `send_json(int code, JsonDocument&)`
  - `require_json_body(JsonDocument&)`
  - `send_ok_with_payload(...)`
- Keep endpoint logic focused on business rules.

**Priority**: Medium

---

### 3.3 Consolidate NTRIP NVS read/write schema definitions
**What**
- Required-key checks and key-by-key mapping appear in both `web_ui.cpp` and `ntrip_client.cpp`.

**Why**
- Duplicated schema knowledge is brittle and easy to desynchronize.

**How**
- Create `ntrip_config_store.*` with:
  - canonical required-keys list
  - load/save functions
  - lockout state accessors
- Reuse from both modules.

**Priority**: Medium

## 4) Logging enhancements

### 4.1 Add event-centric logs for config source and transitions
**What**
- Current logs are informative but mostly line-by-line textual.

**Why**
- Operational debugging is easier with event markers and transition summaries.

**How**
- Introduce event IDs (string constants) for key transitions:
  - `WIFI_CFG_SOURCE=NVS|FILE|SECRETS`
  - `NTRIP_STATE=...`
  - `UART_CFG_APPLY_SUCCESS/FAIL`
- Emit structured key-values where possible.

**Priority**: Medium

---

### 4.2 Add periodic drop-rate and throughput snapshots
**What**
- Drop counters exist (BLE/TCP/NTRIP stream buffers), but derived rates are not consistently logged.

**Why**
- Absolute counters are hard to interpret in the field; rates make saturation visible.

**How**
- Every N seconds, log deltas for:
  - `uart2bleDrops/s`, `ble2uartDrops/s`
  - `uart2tcpDrops/s`, `tcp2uartDrops/s`
  - effective bytes/s per channel
- Optionally expose rate fields in `/api/status`.

**Priority**: Medium

---

### 4.3 Tighten sensitive-data logging policy
**What**
- SSID and password length are logged. This is better than plaintext password logs, but policy is implicit.

**Why**
- Security posture improves with explicit, centralized masking policy.

**How**
- Add `LOG_SENSITIVE(...)` macros gated by a dedicated compile flag (default off).
- Ensure route handlers and setup code use the same policy.

**Priority**: Medium

---

## 5) Efficiency optimization

### 5.1 Reduce dynamic `String` churn in HTTP handlers
**What**
- Multiple handlers build large `String output` from `serializeJson(...)` before sending.

**Why**
- On long-running embedded systems, repeated heap allocations can fragment memory.

**How**
- Stream JSON directly to response client where feasible, or reuse static buffers.
- Pre-size `JsonDocument` capacity where response shape is stable.

**Priority**: High

---

### 5.2 Avoid full rebuild of satellite list on every snapshot request
**What**
- `nmea_get_snapshot()` calls `rebuild_live_sat_list(now)` each request.

**Why**
- If Web UI poll frequency is high, CPU time is spent rebuilding even without new GSV data.

**How**
- Rebuild only when:
  - new GSV data committed, or
  - stale timeout boundary crossed.
- Cache and reuse the live list between requests.

**Priority**: Medium

---

### 5.3 Refine task pacing for low-activity periods
**What**
- Several loops use short fixed delays (`1–10 ms`) even when idle.

**Why**
- Fixed polling can waste cycles and power.

**How**
- Prefer blocking waits where APIs permit (stream buffer receive with timeout already used in parts).
- Tune UART/TCP idle delays with measured CPU load and latency targets.

**Priority**: Medium

---

## 6) Build flags rationalization

### 6.1 Make all boolean flags explicit defaults in `app.h`
**What**
- Most flags are defaulted numerically; `FORCE_HARDCODED_UART` currently isn’t.

**Why**
- Inconsistent defaults make behavior less predictable and docs harder to trust.

**How**
- Add a uniform default block for all booleans (`0/1`).
- Add compile-time dependency checks in one place.

**Priority**: High

---

### 6.2 Publish a single source of truth for flag dependencies
**What**
- Dependency logic appears in `app.h`, `README.md`, and test matrix, with slight drift risk.

**Why**
- Divergent dependency definitions create integration surprises.

**How**
- Create `docs/build-flags.md` generated (or manually synced) from a compact dependency table.
- Reference this from README and build tester.

**Priority**: Medium

---

### 6.3 Rationalize test matrix around orthogonal combinations
**What**
- Current matrix is broad but not obviously minimal/orthogonal.

**Why**
- Matrix bloat increases run time and maintenance while not necessarily improving defect detection.

**How**
- Define tiers:
  - Tier A: smoke (`default`, `full`)
  - Tier B: pairwise orthogonal combos
  - Tier C: negative/constraint tests (e.g., invalid dependencies should fail)

**Priority**: Medium

## Proposed tests to implement

## A) Compile/build flag tests
1. **Boolean flag semantics tests**
   - Build with `-DFORCE_HARDCODED_UART=0` and verify UI unlock behavior at compile-time and runtime API fields.
2. **Dependency negative tests**
   - `-DNTRIP_CLIENT_ENABLE=1 -DWEBUI_ENABLE=0` must fail with expected error.
3. **Matrix minimization set**
   - Keep a canonical set: `default`, `full`, `BLE-only`, `WEBUI+NMEA`, `WEBUI+TCP`, `WEBUI+NTRIP`.

## B) Unit/component tests (host-side where possible)
4. **WiFi config parser/validator tests**
   - valid DHCP/static payloads
   - missing fields
   - malformed IPs
   - empty SSID and masked password pass-through behavior
5. **NTRIP NVS schema tests**
   - missing required key should fail predictably
   - lockout persistence roundtrip
6. **NMEA parser snapshot tests**
   - sentence sequences for RMC/GGA/GSA/GST/GSV
   - stale GSV eviction timing
   - snapshot consistency under rapid feed/read cycles

## C) Integration tests (on-device or HIL)
7. **UART runtime reconfiguration test**
   - POST `/api/config`, assert UART restart and persisted NVS values.
8. **WiFi source fallback test**
   - NVS present -> used
   - NVS absent + `/wifi.json` present -> used and synced
   - both absent -> compile-time fallback
9. **Data plane stress test**
   - Inject bursty RTCM and high-rate NMEA; assert drop counters stay within expected thresholds.
10. **Long-run stability test (8–24h)**
   - monitor heap minimum, reconnect counts, stream continuity, and watchdog resets.

## D) API contract tests
11. **`/api/status` schema contract**
   - required fields present across feature-flag variants.
12. **Error contract tests**
   - all invalid input paths return stable JSON shape (`ok=false`, `error=...`).
